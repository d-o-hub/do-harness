# Heuristics
- **retry transient gh API errors with a bounded script, route deterministic ones around the broken query**: HTTP 502/GraphQL-internal failures replay safely through `scripts/retry.sh`, but the Projects-classic `projectCards` deprecation never succeeds on retry — set PR bodies via REST `PATCH pulls/{N}` and read with explicit `--json` fields instead of default views or `--comments` (from PR #94/#95 triage)
- **a rerun-forbidden or upload-plumbing check failure with zero diff causation is infrastructure, not a finding**: push one empty retrigger commit (`chore(ci): retrigger checks after transient <name> failure`), run one more bounded wait cycle, then escalate if it fails the same way — never merge around it and never commit twice (from PR #94 triage)
- **gh `--json` field names are not guessable: `baseRefOid` does not exist, `baseRefName` does**: copy field lists from the skill scripts (`list-prs.sh`, `checks.sh`) instead of inventing them, and treat `Unknown JSON field` as a skill-text bug to fix, not an API outage (from PR #95 triage)
- **rebase a stacked child with git rebase --onto origin/DEFAULT OLD_PARENT_SHA after any parent merge, then force-push and re-validate**: applies when a parent PR merges (squash or rebase), its branch auto-deletes, and the child auto-retargets to the default branch showing CONFLICTING/DIRTY (from trace 18)
- **a skill that must run at a lifecycle boundary (after opening a PR) needs that trigger in its description; agents load skills from descriptions, not from remembered plans**: skill authoring: lifecycle triggers versus request-only phrasing (from trace 37)
- **optional-tool probes in skills must honor DO_HARNESS_BIN and the repo-local `target/release` fallback (mirroring git-hook resolution) so dev-checkout binaries are found instead of silently falling back to the token-heavy path**: do-harness-optional probes and preflight checks (from trace 37)
- **a wait loop in a skill belongs in a script with a deadline and a terminal summary (PASS/FAIL/PENDING/NONE); an empty API result means not-yet-registered, never done, and the agent never sleeps between calls**: polling PR checks, post-merge runs, or any eventually-consistent API (from trace 38)
- **post-merge verification needs its own bounded helper: an empty run list after a merge means the runs are not registered yet, so it must never be read as success**: default-branch run verification after gh pr merge (from trace 38)
- **a PR can arrive with auto-merge already armed by someone else (observed on this repo: a squash request enabled from the owner account, carrying a synthetic co-author trailer): an armed request merges whatever head exists when GitHub computes mergeability, so it defeats --match-head-commit and can land a head the sweep never validated**: run `scripts/auto-merge.sh PR` during the state check, disarm with `scripts/auto-merge.sh PR --disable` before validating, and halt if the disarm fails; do not treat the eventual merge as your validated-head merge (from PR #181 triage)
- **a PR whose commit range holds a non-lowercase subject can never go green (CI's `check-commitlint.sh --range` lints every non-merge commit) and the guardrail forbids force-pushing an independent PR, so the history cannot be rewritten in place**: replace the branch instead — one lowercase-conventional commit on top of main, a new PR that closes the original and states the reason, and the old PR closed with a link to the replacement; agent-generated branches (for example Jules) freely use uppercase tokens like `PATH` in subjects, so check `git log --format=%s base..head` before adopting one (from PR #179/#188 triage)
- **observed on this repo: a degraded Windows image failed the same install-action step (`bash startup failure`, actions/partner-runner-images#169) identically on `gh run rerun --failed`, while one empty retrigger commit landed a fresh runner where every check passed — and main's equivalent jobs were green minutes before and after; the pinned install-action (2.86.5) already carries the upstream workaround, so the flake is the runner image rather than the action**: distinguish a rerun from a retrigger whenever the failure names a runner-image problem, and escalate only after the fresh runner fails the same way (from PR #195 triage)
- **the untrusted-data contract in a skill that ingests attacker-controlled text must have a sensor behind it, not only prose: lint the ingest scripts for dynamic-execution sinks in CI and assert the contract clause still exists**: applies to pr-triage (PR bodies, comments, diffs, webhook payloads) and any future skill that reads third-party text into an agent session; a sink lint is the honest claim (dangerous sinks absent), a taint tracker is not, and the completion gate is what stops an injected instruction from fabricating a passing result (from PR #132 triage)
- **observed on a downstream repo: three Storage Matrix legs reported CANCELLED ~8 minutes in with no failing step and no annotations, while a plain rerun of the same run succeeded — the check list alone cannot separate that from a failure, and `gh pr checks --watch` reports a cancelled leg as a non-pass that reads like one**: classify `cancelled` as its own outcome with `gh run rerun <run_id> --job <databaseId>` advice (`do-harness ci-explain` emits it), never as a code failure to fix (from rust-self-learning-memory#1041, issue #243)
- **the squash subject is the PR title, so a title carrying an uppercase token turns the default branch red after merge even when the branch range lints clean: `verify`'s commitlint sensor lints the tip commit, and the squash body is the title** (observed on main: `fa0828d fix(hooks): honor core.hooksPath …` left push run 35326494495 with `Failed sensors: commitlint`; a PR titled `… Codecov …` was fixed the same way): GitHub documents the mechanism — "When you squash and merge, GitHub generates a default commit message that you can edit. The default message can include the pull request title, pull request description, or commit information, depending on repository settings and the number of commits in the pull request" (Pull request merges reference, fetched 2026-10-12) — so check the repository's configured default rather than assuming the title lands verbatim, lowercase the title with the branch rewrite (`gh api -X PATCH pulls/N -f title=…`) before merging, and prove the prospective subject locally with `check-commitlint.sh --message <file>` (from PR #296/#297 triage)
- **a bot-updated branch can silently revert recently merged work: the post-merge amend re-applies the bot's pre-merge file states and the update-branch merge resolves toward them, so files the PR never intended to touch come out byte-identical to their pre-fix content** (observed twice: one branch undoing merged PR #295's coverage exit gate, tests and docs; another undoing #292's `pr review` residual policy across `pr/{command,diff,proof,review}.rs`, `tests/pr_review*.rs` and `docs/cli.md`): detect with `git diff origin/main <head> --stat` (intended files plus strangers) and `git diff <merged-commit>^ <head> -- <file>` (empty output = pure revert); fix by restoring each reverted file verbatim from main and keeping only the intended change, then run the reverted PR's own tests — the branch's own suite cannot fail on work it deleted (from PR #294/#296 triage)
- **on own or bot-authored branches, rewriting the offending historical subject in place is the supported fix; the replace-the-branch route is only for foreign PRs, which the guardrail forbids force-pushing**: a tree-identical `filter-branch --msg-filter` + `push --force-with-lease` keeps the pull request, its threads and its base, whereas replacing the branch loses all three (observed on three rewrites that then went 12/12–15/15 green): enumerate offenders with `check-commitlint.sh --range origin/main...<branch>` first, re-lint after the rewrite, and expect the pre-push hook's full verify to outlive a capped shell job — run the targeted targets locally and let CI re-gate the pushed head (from PR #293/#296/#297 triage)
