# 0.4.0 Roadmap: Measurable Workflow Efficiency With Trustworthy Feedback

**Status:** analysis complete; WF-01–WF-12 are implemented and verified; WF-13–WF-14 remain not scheduled.
**Research cutoff:** 2026-10-28.  
**Release theme:** measurable workflow efficiency with trustworthy feedback.

## Context

The workspace version is `0.3.7` (`Cargo.toml:7-10`). A previously inspected `target/release/do-harness` reported `0.3.6` / `ed76dad` / dirty; that stale binary is not evidence of current-source behavior. This roadmap records source inspection and primary-source research. All scheduled roadmap features (WF-01–WF-12) were subsequently implemented and verified; their exact tests, CLI smoke, and artifact identity are in the [progress record](v0.4.0-progress.md). No benchmark, performance improvement, or GitHub publication is claimed.

The 0.4.0 opportunity is to lower the effort and context consumed by a complete development workflow while retaining correctness, useful PR review, honest measurements, and safe feedback. The release centerpiece should be a review-context payload plus impact-gated GitHub feedback. Repeated agent-eval trials are a supporting feature, not the theme.

## Prioritized recommendations

Each card records its problem, source evidence, impact, behavior, reuse/dependencies, and observable acceptance. WF-01–WF-12's implementation and verification status are explicit; the remaining cards (WF-13–WF-14) remain not scheduled.
### WF-01 — Bound agent-eval process capture and cleanup (P0; already implemented)

- **Problem:** At analysis time, agent-eval accumulated unbounded stdout/stderr vectors and waited on reader joins without a cleanup deadline. Descendants retaining inherited pipes could delay completion.
- **Evidence:** Streamed redacted capture and the 1 MiB output bound are implemented in `crates/do-harness/src/eval/agent.rs:35-36,100-150,169-240,242-353`; process-group setup and the two-second cleanup budget are in `crates/do-harness/src/shell.rs:16,98-145`. Acceptance tests are in `crates/do-harness/src/eval/agent_tests.rs:225-303`. The targeted tests reproduced the output-limit, secret-leak, and descendant-delay failures before the fix; post-fix results and the CLI smoke artifact identity are in the [progress record](v0.4.0-progress.md).
- **User impact:** bounded retention prevents output-driven memory growth and sensitive environment-value leakage; process-tree termination prevents ordinary descendants from holding completion open.
- **Implemented behavior (verified):** stdout/stderr stream through the existing redactor; combined raw output is limited to 1 MiB; retained `agent_stdout.txt` is capped at 1 MiB; POSIX children use a private process group. Shared tree cleanup uses a two-second pipe-drain budget, preserves Windows `taskkill /T`, and reports unverified cleanup. Grading still reads the separate saved stdout artifact.
- **Reuse / dependencies:** existing sensor-capture/redaction patterns and shared shell process helpers. The WF-01 prerequisite for WF-12 and safe-log dependency for WF-09 is satisfied on the tested Linux path.
- **Acceptance:** verified on Linux: oversized output fails with bounded `agent_stdout.txt`; timed-out and successful-parent descendants inheriting pipes do not delay completion beyond the regression-test budget; synthetic secrets are absent from retained failure text and stdout artifact. The Windows `taskkill` path remains untested and is the next check.

### WF-02 — Keep eval JSON stdout parseable on every outcome (P0; already implemented)

- **Problem:** At analysis time, text diagnostics were printed to stdout in JSON mode for grader drift, strict-fixture warnings, score/lift floor misses, and bless results, so stdout contained unparseable text mixed with JSON.
- **Evidence:** `crates/do-harness/src/eval/orchestrator.rs:69-85,136-157,260-266,306-347`; `crates/do-harness/src/eval/bless.rs:38-62`; `crates/do-harness/src/eval.rs:12-21`. End-to-end integration tests in `crates/do-harness/tests/eval_json.rs:1-300` failed 6/6 before the fix and passed 6/6 after.
- **User impact:** automation can reliably parse the machine-readable report across every outcome, including failure, warning, drift, and bless paths.
- **Implemented behavior (verified):** In JSON mode, `super::diag!` routes text diagnostics to stderr, leaving stdout dedicated solely to the serialized report array; empty or early-drift evaluations emit `[]`. Exit codes (0 for pass/warning/bless/dry-run, 1 for strict miss/drift/bar miss, 2 for usage errors) and report contents are strictly preserved.
- **Reuse / dependencies:** existing `Format::Json` and eval report schema. Satisfies the JSON parseability requirement for downstream automation.
- **Acceptance:** verified across all six scenarios in `tests/eval_json.rs`: success with advisory warning, strict-fixture failure, bless, grader drift, bar miss, and dry-run each produce stdout that parses completely as one JSON array value while keeping their respective exit codes.

### WF-03 — Add a compact agent-facing PR review payload (P1; already implemented)

- **Problem:** At analysis time, `measurement.t_res` counted only serialized residual units while JSON emitted the complete pretty `ReviewReport` including full exempt/skipped units. The measured quantity was not the delivered payload.
- **Evidence:** `crates/do-harness/src/pr/agent_view.rs:1-270`; `crates/do-harness/src/pr/command.rs:97-107,192-237`; `crates/do-harness/src/cli/actions.rs:137-140`. Integration coverage in `crates/do-harness/tests/pr_review_agent.rs:1-290` verifies all 7 acceptance contract fixtures.
- **User impact:** reviewers and agent integrations receive a compact, versioned envelope without paying for audit-only lines, with emitted-byte accounting measured at the envelope boundary.
- **Implemented behavior (verified):** `do-harness pr review [PR | --base REV --head REV] --view agent|audit --format json` emits `AgentReviewEnvelope` in agent mode; `audit` remains the default and emits `ReviewReport`. The agent envelope carries all review-required units, exemption/proven identities (without lines), revoked-proof reasons, and markers (`binary`, `rename-only`, `mode-change`, `parse-uncertain`). It compares candidate JSON representations (structured residual vs raw diff) and selects the smaller complete payload.
- **Reuse / dependencies:** existing parser, proof matcher, merge-base policy probe, `ReviewReport`, and cache. Satisfies the review-context contract for downstream agents.
- **Acceptance:** verified across all seven contract fixtures in `tests/pr_review_agent.rs`: source plus lockfile exemption, malicious policy in PR head, malformed policy, planted public-contract defect, rename/mode/binary changes, no policy, and tiny diff selecting raw_diff representation.

### WF-04 — Look up PR review cache before materializing the diff (P1; already implemented)

- **Problem:** At analysis time, range review resolved merge base and head, then ran `git diff`; only later did `assemble` check the cache.
- **Evidence:** `crates/do-harness/src/pr/review.rs:115-215,285-325`. Integration coverage in `crates/do-harness/tests/pr_review_cache.rs:1-260` proves zero `git diff` invocations on warm cache hits and verified rebinding of target metadata.
- **User impact:** warm reviews avoid unnecessary git diff subprocess execution while callers with different target refs or modes receive correct rebound metadata instead of cached caller metadata.
- **Implemented behavior (verified):** `analyze` checks the cache immediately after resolving merge base, head SHA, and merge-base policy digest. On a hit, `cached_report` rebinds `mode`, `pr`, `base`, and `head` to the caller's request, leaving substantive analysis intact and bypassing `local_diff`. Cache misses and `recompute` run `local_diff`, assemble, and store.
- **Reuse / dependencies:** existing `CacheKey`, cache storage, report parser, and policy probe.
- **Acceptance:** verified in `tests/pr_review_cache.rs`: an instrumented warm review performs 0 `git diff` invocations while serving the cached result; requesting the same commits via `--base HEAD~1` rebinds `base: "HEAD~1"`; changed head or policy recomputes and invokes diff.

### WF-05 — Measure the complete workflow, not a proxy (P1; already implemented)

- **Problem:** At analysis time, the paired benchmark reported `token_cost: null`, `currency_cost: null`, and no external model version, and its summary omitted end-to-end median/p95, repair cycles, and context bytes.
- **Evidence:** `scripts/workflow_benchmark/runner.py:110-335`. Test suite in `scripts/workflow_benchmark/tests.py:110-180` verified trusted adapter usage capture, reasoned null preservation, resource limits, and nearest-rank median/p95 summary calculations.
- **User impact:** developers and evaluators get honest end-to-end workflow measurements covering verification and repair, without converting bytes to artificial tokens or mistaking partial job runtimes for user latency.
- **Implemented behavior (verified):** `runner.py` measures complete workflow duration at the execution boundary (`elapsed_ms`), tracks cumulative `verification_ms`, and counts `repair_cycles`. It accepts optional adapter token/currency usage and model version when emitted by the adapter or passed via `--model-version`, preserving reasoned nulls when unavailable. Summaries compute nearest-rank median and p95 for elapsed time and verification time, alongside repair cycles, context bytes, and token cost totals.
- **Reuse / dependencies:** existing corpus, grader, bounded executor, paired order, and runner protocol; no second runner.
- **Acceptance:** verified via `python3 scripts/workflow-benchmark.py --self-test` (12 tests passed): environment carries CPU count and model identity; resource limits match budgets; trusted adapter records token/currency cost; untrusted or missing usage preserves reasoned nulls; summary computes median/p95, repair cycles, and context byte totals.

### WF-09 — Add impact-gated GitHub feedback and verified learning (P1; already implemented)

- **Problem:** At analysis time, beats, error signatures, and `learn --draft` supported local self-correction, but no issue-creation surface existed, and frequency alone risked confusing downstream application failures with harness defects.
- **Evidence:** `crates/do-harness/src/feedback/**`; `crates/do-harness/src/cli/actions.rs:333-386`. - **User impact:** attributable harness defects can be published or linked safely to GitHub without exposing secrets, creating duplicate storms, or requiring human intervention when running under automated CI swarms.
- **Implemented behavior (verified):** `do-harness feedback draft --repo OWNER/REPO` generates local-only candidate proposals; `feedback submit --draft <FILE> [--yes]` verifies explicit confirmation, runs remote deduplication across open and closed issues, and creates/links the issue via fixed argv; `feedback auto --repo OWNER/REPO [--dry-run]` provides an unattended pipeline with a 1-issue circuit breaker. Excerpts are sanitized via the credential redactor. Qualification distinguishes sensor retries from independent verification runs (grouping runs within a 60s cooldown) and filters expected ATDD-red phase tests and consumer test failures.
- **Reuse / dependencies:** existing beats, error signatures, events, and `Redactor`.
- **Acceptance:** verified via `cargo test --test feedback` and `cargo test --test feedback_attribution`: 0 candidates from under-threshold fires; retries in a single run count as 1 incident and remain under threshold; 3 independent runs qualify; expected ATDD-red checks are filtered by the attribution gate; 1 severe crash/panic qualifies without recurrence; duplicate beat/event counts once; repeat submission links existing issue without creating duplicates; auth failures preserve draft files; synthetic secrets are redacted with `[REDACTED]`; unattended `--auto` mode runs end-to-end without interactive prompts.

### WF-12 — Add opt-in repeated agent-eval trials (P2; already implemented)

- **Problem:** At analysis time, one stochastic agent run could not estimate per-case variability; choosing the best of repeated attempts would overstate reliability and shared residue can contaminate later attempts.
- **Evidence:** `crates/do-harness/src/eval/agent.rs:50-95`; `crates/do-harness/src/eval/orchestrator.rs:45-80,165-215`; `crates/do-harness/src/cli.rs:323-326`. Integration test suite in `crates/do-harness/tests/eval_trials.rs:1-210` verifies controlled pass/fail/pass trial reporting (2/3 = 0.67), zero residue crossing trials, default 1 trial, and `--trials 0` exit 2 rejection.
- **User impact:** maintainers obtain trustworthy variability evidence across repeated agent evaluation runs without risk of false passes or residue contamination between attempts.
- **Implemented behavior (verified):** `do-harness eval --trials N` runs `N` sequential trials per case in fresh, isolated sandboxes. Each trial's outcome is recorded in `cases[].trial` and merged into aggregate assertion-weighted pass rates. The text report line renders `trials={N}` when `N > 1`, and the JSON report emits `"trials": N`. Baseline absence remains unmeasured (`null`), and `--trials 0` exits 2 as a usage error.
- **Reuse / dependencies:** existing sandbox, grader, and aggregate types. Pre-requisite WF-01 (bounded capture/cleanup) was satisfied.
- **Acceptance:** verified via `cargo test --test eval_trials` (3 tests passed): controlled pass/fail/pass script reports 2 passed out of 3 graded assertions (pass_rate ~0.67); trial residue does not cross sandboxes; default trials is 1; missing baseline remains null/unmeasured; `--trials 0` fails with usage error (exit 2).

### WF-13 — Retain rejected and deferred decisions (not scheduled)

- **User impact:** repeating rejected experiments or presenting historic figures as new results wastes effort and can lower review/test confidence.
- **Proposed behavior:** keep semantic routing and affected-component selection closed; keep automatic multi-candidate guidance mutation deferred. Reopen only with materially different, predeclared evidence and decision gates. Do not present historical figures as newly measured performance.
- **Reuse / dependencies:** preserve the existing decision records and corpora; no new router or learner.
- **Acceptance:** the roadmap links each prior verdict and creates no implementation/issue for these rejected paths; a future reconsideration must name new evidence, test sensitivity, resource parity, correctness gates, and a measured benefit before implementation.

### WF-14 — Evaluate workflow lockfiles as an optional supply-chain control (not scheduled; no release dependency)

- **Problem:** mutable action tags/branches and transitive dependencies are a supply-chain concern; the repository's existing offline checker proves reference shape, not that a referenced commit exists or is safe.
- **Evidence:** GitHub announced a public preview on 2026-10-14 and general availability on 2026-10-28; lockfiles cover actions, transitive dependencies, reusable workflows, gradual onboarding, stale checks, and an optional Require lockfile policy. The current checker intentionally requires full SHAs/digests and is offline (`scripts/action_pins/references.py:1-11`).
- **User impact:** lockfiles may provide additional dependency-resolution guarantees, but adopting them without reconciling the current full-SHA policy or reviewing locked dependencies could create false security claims.
- **Proposed behavior:** record an optional repository-local evaluation, not an automatic migration or 0.4.0 gate. Retain current full-SHA/digest enforcement. A separate reviewed policy decision is required before changing accepted workflow syntax; a lockfile does not establish dependency safety.
- **Reuse / dependencies:** GitHub's `gh actions-lock` extension, current action-pin checker, and existing workflow review. This is supply-chain research, not a source dependency for the release theme.
- **Acceptance:** an isolated trial demonstrates lockfile generation for direct/transitive/reusable-workflow dependencies and stale-lock detection, identifies any conflict with the current checker, and leaves production workflows and checker policy unchanged unless a separately reviewed decision authorizes migration.

## Feature contracts

### Review-context contract

Proposed interface: `do-harness pr review [PR | --base REV --head REV] --view agent|audit --format json`. This is not a shipped CLI option. `audit` remains the default and retains the full existing report.

- The agent view is a compact, versioned envelope bound to the resolved head SHA, merge base, and policy digest. It carries all warnings and revoked-proof reasons, plus counts and identities for audit-only exemptions; only the agent view omits exempt/skipped payload lines. The complete audit report remains available.
- Serialize complete residual content. Compare the actual candidate envelope with an equivalently enveloped raw-diff representation and choose the smaller complete payload. Do not truncate hunks, substitute an LLM summary for source, or represent an omitted change as reviewed. Include a representation discriminator and explicit review-required unit identities so consumers know what content the envelope contains.
- With no valid policy, every changed unit remains review-required. Binary, rename, mode-only, and parse-uncertain changes receive explicit review-required markers. Policy continues to be read from the trusted merge base, never from the PR head.
- Report actual UTF-8 bytes of the emitted agent envelope separately from full audit-report bytes. Token and currency fields stay unknown unless a named tokenizer/provider adapter measures them; bytes divided by four is not a token measurement.
- Reuse the current parser, proof matcher, merge-base policy probe, and cache. Add no model router or merge authority.
- Acceptance fixtures: source plus lockfile exemption; malicious policy added in the PR head; malformed policy; planted public-contract defect; rename, mode, and binary changes; no policy; and a tiny diff for which raw form is smaller. Every review-required unit survives exactly once. Exemptions remain visible by identity in the audit trail.

### Impact-feedback and learning contract

Both commands below are proposed, not shipped. Drafting is local-only; publication is a separate explicit action. This analysis creates no issue.

- Local entry point: `do-harness feedback draft --repo d-o-hub/do-harness --days 30 --format json`. Generate candidates only from explicitly recorded failures or linked benchmark evidence. An adopting repository must choose its own issue target explicitly; a consumer application's ordinary failing test is not automatically a harness defect.
- Candidate eligibility requires actionable harness impact: a reproduced harness defect, verified safety/incorrect-green regression, or repeated root-cause-attributed workflow problem. Reuse the existing three-fire/30-day recurrence default, but count independent attributable occurrences, not retries or a beat duplicated in an event file. Frequency alone is insufficient.
- Performance/token candidates require comparable before/after evidence of a regression or measured improvement opportunity with unchanged correctness. Routine successful runs, expected ATDD-red checks, resolved duplicates, minor wording changes, and unmeasured speculation produce no issue candidate.
- A local draft contains a stable fingerprint, target repository, source IDs, build/head identity, observed versus expected behavior, impact rationale, minimal reproduction, bounded redacted diagnostic excerpt, and suggested verification. Prompts, raw environment dumps, entire logs, private code, and secret-bearing attachments are excluded by default. Suspected sensitive security reports remain local for private disclosure.
- Submission is explicit: `do-harness feedback submit --draft FILE --repo d-o-hub/do-harness`. Before publication, show and review the exact sanitized title/body and target. Ordinary `verify` and `feedback draft` never publish.
- Deduplicate by target repository plus normalized failure fingerprint and relevant contract/build identity. Store an opaque marker in issue bodies and a local issue-link receipt. Search both open and closed issues before creation. Link a match locally; do not automatically comment, reopen, or duplicate. A verified regression after a closed fix yields a fresh reviewed draft linked to the prior issue.
- Use fixed argv, not shell interpolation: `gh issue create --repo OWNER/REPO --title TITLE --body-file -`; targeted search can use `gh issue list --repo OWNER/REPO --state all --search QUERY --json number,url,state,body`. Unknown authentication, incomplete search, rate limits, and uncertain publish outcomes fail closed: keep the draft and reconcile before retrying; never blindly repost.
- Retain only impactful incident metadata and bounded redacted excerpts locally. Reuse beats/traces rather than duplicating every tool action. `docs/retention.md:5-10` currently prunes beats but not traces; propose configurable trace/feedback retention while preserving minimal issue/learning receipts. Never delete hash-chain workflow events or bless approvals.
- Learning remains a reviewed proposal cycle: incident → reproduced root cause → verified fix → trace → concise `learn`/`distill` heuristic proposal → held-out regression/skill eval → reviewed promotion. Never auto-edit instructions, weaken graders, lower baselines, or bless a rule merely because it reduces failures. Record source IDs, affected guide, and verification result; suppress proposals without demonstrated improvement.
- Acceptance: zero candidates from routine passes or expected test-red; one candidate from three independent attributable incidents; one severe reproduced incident can qualify without recurrence; duplicate beat/event counts once; repeat submission links the existing issue; authentication/ambiguous failures preserve the draft; a synthetic secret never reaches draft, logs, or issue payload; a heuristic failing held-out regression is not promoted.

## Measurement and acceptance

Measure the complete path: repository inspection and context loading → edit → selected checks → repair → strict verification → PR review/readiness. Compare equal correctness and coverage. Include Rust, Node/TS, and a generic custom-sensor repository; do not claim automatic optimization for arbitrary codebases.

For each prospective performance slice, predeclare five paired cold-cache and five paired warm-cache runs. Keep cold and warm results separate. Use the same workload, source/build/model/tool identity, resource limits, concurrency policy, and verification coverage in each pair. Report every sample, median and p95, total delivered context bytes, recorded tool calls and verification invocations, first-attempt success, repair cycles, correctness/defect-detection results, and any known provider usage. Record actual end-to-end elapsed time; do not add parallel job medians and call that user-visible latency.

A candidate is beneficial only when the measured target improves without losing a required defect detection, increasing repair work, or worsening p95 in the predeclared sample. There is no universal percentage promise. Paid model usage is measured only through an explicitly configured trusted adapter; absent usage remains null with an explicit reason. Never infer measured tokens from bytes. The six cases in `benchmarks/workflow-v1.json:11-129` remain correctness fixtures, not cross-language real-world productivity evidence.
